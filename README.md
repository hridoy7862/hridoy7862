## About

I am an **RTL Design & Verification Engineer** with a B.Sc. in Electrical & Electronic Engineering from the **Rajshahi University of Engineering & Technology (RUET)**. My work is centered on designing and verifying digital systems at the RTL and subsystem levels, with emphasis on **processor pipelines, AMBA interconnects, memory subsystems, FPGA-based SoCs, and protocol-driven control logic**.

My broader technical interests extend toward **hardware and SoC security, computer architecture, hardware trust, logic locking, hardware Trojan detection, FPGA architecture, VLSI design, and AI for EDA**.

I build verification environments around architectural intent rather than isolated signal checks. My projects use constrained-random stimulus, reusable transaction-level components, independent reference models, self-checking scoreboards, SystemVerilog Assertions, functional coverage, formal properties, fault injection, and automated regression flows.

My current target roles are **Design Verification Engineer, SoC Verification Engineer, CPU Verification Engineer, and RTL Design Engineer** positions where debugging depth, coverage closure, and microarchitecture understanding are core requirements.

## Engineering Approach

```text
Specification and architectural intent
                ↓
Verification plan and risk decomposition
                ↓
Stimulus + monitors + assertions + reference models
                ↓
Scoreboard and end-to-end correctness checks
                ↓
Functional, assertion and code coverage analysis
                ↓
Targeted regressions, root-cause debug and closure
```

- Treat assertions as executable interface and microarchitecture requirements.
- Keep scoreboards independent from DUT implementation details wherever practical.
- Verify backpressure, error propagation, reset interruption and illegal behavior—not only nominal traffic.
- Use coverage to expose missing scenarios, not as a substitute for correctness checks.
- Preserve deterministic logs and transaction traces so regressions remain debuggable at scale.
- Use architectural reference models to separate expected behavior from DUT implementation details.
- Debug from transaction-level behavior down to RTL signal-level waveforms.
- Prefer reusable verification components over test-specific procedural code.

## Verification Philosophy

### 1. Verify the architecture, not only the signals

Verification should compare the DUT against intended architectural behavior rather than simply checking whether individual signals toggle correctly.

### 2. Maintain an independent reference model

Expected behavior should be generated independently wherever practical so that the scoreboard does not simply reproduce DUT implementation logic.

### 3. Combine dynamic and formal verification

Dynamic simulation is useful for realistic traffic and system scenarios, while formal properties can exhaustively explore selected protocol and state-transition behaviors.

### 4. Use coverage to identify verification gaps

Coverage is used to determine which scenarios have not been exercised and to guide additional stimulus.

### 5. Debug systematically

```text
Failure
  ↓
Waveform / Log
  ↓
Transaction Trace
  ↓
Protocol Check
  ↓
Reference Model Comparison
  ↓
Root Cause
  ↓
RTL / Testbench Fix
  ↓
Regression
```
